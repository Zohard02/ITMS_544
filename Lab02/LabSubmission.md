## Q1. State is a secret

At least four secrets end up in the Terraform state of this lab: the generated Cognito administrator password (`random_password.admin`, also exposed as the sensitive output `admin_password`), the internal service token (`random_password.token_current` and `token_previous`, and the value of the SSM SecureString parameters that hold them), the private keys of the internal certificate authority and of every service (`tls_private_key` in `pki.tf`), and the key that signs the Flask session cookies. Terraform has to store them because it generates them itself with the `random` and `tls` providers, and the state is the only record of what it created: without the stored values every `plan` would produce new passwords and keys and replace the resources that use them, and Terraform could not compare the values in AWS (for example, an SSM parameter) with what it expects or return the outputs. Marking a value `sensitive` only hides it on screen; it is still written to the state in clear text.

The state bucket `lab02-tfstate-083163125365` is protected by all four Block Public Access settings, `BucketOwnerEnforced` object ownership (ACLs disabled, only policies decide), default SSE-S3 (AES256) encryption with a bucket key plus `encrypt = true` in the backend, versioning (an older state can be recovered after corruption or a bad write), a lifecycle rule that expires old versions after 30 days, and a bucket policy that denies any request that does not use HTTPS (`aws:SecureTransport = false`). Outside the bucket, `.gitignore` excludes `*.tfstate`, `*.tfplan` and `terraform.tfvars`, so the state never reaches Git. The S3 lock object (`use_lockfile = true`) creates `lab02/terraform.tfstate.tflock` in the bucket while a `plan` or `apply` runs, so a second run cannot acquire the lock and two people (or two terminals) cannot write the state at the same time and overwrite or corrupt each other's changes; since Terraform 1.10 this no longer needs a DynamoDB table.

## Q2. What makes a subnet private?

A subnet is private when its route table has no route to an internet gateway and its instances have no public IP address, so nothing on the internet can start a connection to them. In `network.tf`, `public_a` is public because the association on lines 57–60 (`route_table_id = each.value.public ? aws_route_table.public.id : aws_route_table.private.id`, with `public = true` for `public_a` in `locals.tf` line 15) places it in the public route table, whose route on lines 39–43 sends `0.0.0.0/0` to `aws_internet_gateway.igw`. `private_a` (`public = false`, `locals.tf` line 17) is placed in the private route table, whose only default route on lines 51–55 points to the NAT instance's network interface. In addition, line 29 sets `map_public_ip_on_launch = false` for every subnet and only the web server and the NAT instance request a public address (`compute.tf` lines 22 and 41); in H1 the onboarding (10.20.11.10), offboarding (10.20.12.10) and dashboard (10.20.11.11) servers showed no public IP.

If someone added a route to the internet gateway in the private route table, it would replace the default route through the NAT instance. Because the private servers have no public IP, the internet gateway could not translate their traffic, so they would lose all outbound access: SSM, CloudWatch Logs and the Cognito JWKS would become unreachable and the services would fail. The subnet would also be one step away from exposure, because assigning a public IP to any instance would make it directly reachable, leaving only the security groups and network ACLs in the way.

The lab uses a NAT instance because a `t3.micro` NAT instance is covered by the Free Tier, while a managed NAT gateway is billed per hour and per gigabyte processed even when idle. The trade-off is that the NAT instance is ours to harden and patch, is a single point of failure in one AZ, has limited bandwidth, and its forwarding depends on our own iptables rules (it only forwards port 443 from the VPC). A NAT gateway is managed, highly available inside its AZ and scales automatically, but costs money and still gives the private subnets general internet egress. Interface endpoints (PrivateLink) are the most secure option because traffic to AWS APIs never leaves the AWS network and the subnets need no internet egress at all, but each endpoint is billed per hour per AZ, several would be needed (SSM, SSM messages, EC2 messages, CloudWatch Logs), and non-AWS destinations such as the Python package index would still need a NAT. The lab already uses the free S3 gateway endpoint for S3.

## Q3. Two firewalls

Rule 120 in the public network ACL allows TCP 1024–65535 from `0.0.0.0/0`, and port 8443 is inside that range. Network ACL rules are evaluated in number order and the first match wins, so without rule 105 (deny 8443 from everyone), any address that did not match rule 100 (allow 8443 from `52.124.37.145/32`) would still be allowed by rule 120. Rule 105 makes the ACL refuse the console port to everyone except the admin address, as a second layer behind the security group. The ACL needs reply rules because it is stateless: it evaluates every packet on its own, so the reply to an outgoing connection, which returns to a random ephemeral port, must be explicitly allowed (rule 120 inbound, rule 120 outbound). A security group is stateful: it tracks connections, so the reply to an allowed connection is allowed automatically.

A network ACL can do things a security group cannot: it can explicitly deny traffic (rules 105 in both ACLs) and it applies to every instance in the subnet, including one launched by mistake with a permissive security group. A security group can do things an ACL cannot: it applies per network interface and can reference another security group as the source, so the private services accept ports 5001–5003 only from the web server's security group rather than from a whole CIDR range.

## Q4. One server, one role

Giving every microservice its own server and IAM role limits the blast radius of a compromise and enforces least privilege: an attacker who takes over the dashboard service only gets read-only IAM permissions, not the onboarding service's ability to create users or the offboarding service's ability to attach the deny-all policy. It also makes accountability clear, because CloudTrail records each call under a distinct role session (in the incident drill, `CreateUser` was made by the onboarding instance `i-0f620facf021628e9` and `AttachUserPolicy` for the offboarding by `i-0ccf9b9aad42c06fa`). With one shared role, every service would hold the union of all permissions and one vulnerability would expose all of them.

In `svc-onboarding.json.tftpl`, the statement `AttachOnlyTheMFAGuardPolicy` allows `iam:AttachUserPolicy` only with the condition `"ArnEquals": {"iam:PolicyARN": "arn:aws:iam::<account>:policy/nimbus/Nimbus-RequireMFA"}`. The policy simulator confirmed it: attaching `AdministratorAccess` to `user/nimbus/james` returned `implicitDeny`, attaching `Nimbus-RequireMFA` returned `allowed`, and `iam:CreateLoginProfile` on my own `lab-user` (outside `/nimbus/`) returned `implicitDeny`. If the policy were careless, for example `AttachUserPolicy` without that condition, a compromised onboarding service could create a new user under `/nimbus/`, attach `AdministratorAccess` to it, give it a console password with `CreateLoginProfile`, and log in as a full administrator. Similarly, because `AddToNimbusGroupsOnly` allows any group under `/nimbus/`, a powerful group created there would become an escalation path.

## Q5. Layers between services

The network rules (security groups and ACLs) stop anyone outside the web subnet from even reaching the services: in H1 ports 22, 5001 and 8080 timed out from my container and the flow log recorded the packets as REJECT. They do not stop an attacker who already runs code on the web server, because that host is an allowed source. Mutual TLS stops any host that does not hold a certificate signed by the internal CA, including a rogue instance inside the VPC, and protects the traffic from eavesdropping and man-in-the-middle attacks: in H2 the request without a client certificate failed during the handshake (`000`). It does not stop an attacker with root on the web server, who can read `/etc/nimbus/tls/service.key`, because mTLS authenticates the machine, not the person. The internal token stops a caller that has a valid certificate but not the shared secret (H2 request 2 returned `401` and the dashboard logged `internal_auth_rejected` from `10.20.1.10`), and it can be rotated without downtime (I1, versions 1 → 3). It does not stop an attacker who can call `ssm:GetParameter` with the web server's role, as H2 itself showed when it read the token. The administrator JWT stops any request that is not backed by a real administrator who signed in with password and MFA (H2 request 3 returned `401`, and in H3 a token edited to say `mallory` was refused with `InvalidSignatureError`). It does not stop the misuse of a stolen, still-valid token during its lifetime, or a compromised administrator account.

The certificates live only 72 hours (`validity_period_hours = 72` in `pki.tf`) because the lab has no revocation infrastructure (no CRL or OCSP): a short lifetime limits how long a stolen private key remains useful, forces issuance to be automated, and matches servers that are replaced rather than patched and that shut themselves down after five hours.

## Q6 (explore). Where should secrets live?

**Rotation.** AWS Secrets Manager has built-in rotation: it can rotate secrets on a schedule using a Lambda function, with managed rotation for supported databases, and it keeps staging labels such as `AWSCURRENT` and `AWSPREVIOUS`. SSM Parameter Store has no native rotation; the lab implements it by hand with two parameters (`current` and `previous`) and `rotate_token.sh`. HashiCorp Vault goes further with dynamic secrets: it creates short-lived credentials on demand (for example, database users or AWS credentials) with a lease, and revokes them when the lease expires, so there is often nothing long-lived to rotate.

**Cost.** Standard Parameter Store parameters, including SecureString, cost nothing to store; advanced parameters and higher throughput are charged, and KMS charges apply for customer managed keys. Secrets Manager costs $0.40 per secret per month plus $0.05 per 10,000 API calls. Vault Community Edition has no licence fee but you pay for the servers, storage, high availability and the people who operate and unseal it; the managed HCP Vault service is a paid subscription.

**Auditing.** Parameter Store and Secrets Manager calls are recorded by CloudTrail, which shows who read or changed which secret and when, and can feed EventBridge alerts. Vault has its own audit devices that log every request and response (with secret values hashed), and it works the same across clouds and on-premises, but those logs are separate from CloudTrail.

**Access control.** Both AWS services use IAM identity policies (as in this lab, where each service role may read only its own key and the token parameters) and KMS key policies; Secrets Manager also supports resource-based policies and cross-account sharing. Vault uses its own policies attached to tokens, with many authentication methods (including AWS IAM, Kubernetes, OIDC), which suits multi-cloud environments.

Secrets that Terraform generates are still exposed through the state file because Terraform must persist every resource attribute, including `random_password.result`, `tls_private_key.private_key_pem` and the SSM parameter `value`, to detect changes in the next plan; encryption at rest in S3 does not help anyone who can read the state. Two ways to avoid it are: (1) do not let Terraform know the secret at all, by letting the service generate and rotate it (for example, a Secrets Manager secret with managed rotation, or RDS-managed master passwords) and passing only the ARN to the application, which reads the value at runtime; and (2) use Terraform's ephemeral resources and write-only arguments (available in recent Terraform versions), which pass a value to the provider without ever writing it to the plan or state. A third, complementary measure is to treat the state as a secret: restrict who can read the bucket, encrypt it with a customer managed KMS key, and audit access.

## Q7. Anatomy of a JWT

A JWT has three parts separated by dots: the header, the payload and the signature, each base64url-encoded. The token I decoded in H3 had the header `{'kid': 'pI/3HvLFui02iYSn7iyggBaZAugbLiUeixMIuHtuTfU=', 'alg': 'RS256'}` and a payload with `iss` (my user pool `us-east-2_5ed9plX3s`), `client_id`, `token_use: access`, `username: admin`, `cognito:groups: ['admins']` and `exp`. None of the three parts is encrypted: this is a signed token (JWS), so anyone who holds it can read the payload; only the signature protects it from being changed, which is why the forged copy with `username: mallory` was refused with `InvalidSignatureError`.

`verify_jwt` in `cognito_auth.py` checks that the token has three parts; fetches the public key named by `kid` from the pool's JWKS and verifies the signature; accepts only `RS256`; requires `exp`, `iat`, `iss` and `sub` and rejects expired tokens; checks that `iss` is our user pool; checks that `token_use` is `access`; checks that `client_id` is our app client; and checks that the user is in the `admins` group. The fixed algorithm list prevents the `alg: none` and algorithm-confusion attacks, in which an attacker sets the header to `none` or to `HS256` and signs with the public key as if it were a shared secret, so a library that trusted the header would accept a forged token. The `token_use` check prevents an ID token, which has a different purpose and audience, from being replayed as an access token; and the `client_id` and `iss` checks prevent a validly signed token from another app client or another user pool, possibly one controlled by the attacker, from being accepted.

## Q8 (explore). The limits of a bearer token

A JWT is verified locally with the public key, without asking Cognito, so once it is issued it stays valid until `exp` even if the administrator leaves, the password is reset or the account is disabled: whoever holds the token is treated as the administrator. This is the revocation problem of bearer tokens. The lab reduces it by giving the access token a 30-minute lifetime (`access_token_validity = 30` minutes in `cognito.tf`, and the console session cookie also expires after 1,800 seconds, as I saw when the dashboard sent me back to the sign-in page): a stolen token is useful for at most 30 minutes, and getting a new one requires the refresh token (valid for one day), which Cognito can revoke (`RevokeToken`, `AdminUserGlobalSignOut`). The residual window can be closed further with shorter lifetimes or a deny list of token IDs checked by the services.

The lab uses `USER_PASSWORD_AUTH`: the web application receives the administrator's username and password in its own form and sends them to the Cognito API, then handles the TOTP challenge itself. It is simple and needs no domain or redirects, but the application sees the password, and it must implement MFA prompts, lockout and error handling itself (which is exactly where bug 9 of this lab was). With the OAuth 2.0 authorization code flow with PKCE and the Cognito hosted UI (now called managed login), the browser is redirected to Cognito's own sign-in pages, which handle the password, MFA, federation and account recovery; Cognito then returns a one-time authorization code to a registered redirect URL, and the application exchanges it for tokens at the token endpoint. PKCE adds a random code verifier whose hash (code challenge) is sent in the first request, so an intercepted authorization code cannot be redeemed by anyone else. In production I would use the authorization code flow with PKCE and managed login, because the application never handles credentials, it reduces phishing and implementation risk, it gives standard support for MFA and identity federation, and it is the flow recommended by current OAuth security guidance; `USER_PASSWORD_AUTH` is acceptable for a lab or a trusted internal tool.

## Q9. Plan, drift and immutable servers

The first `terraform apply` created **163 resources** (`Apply complete! Resources: 163 added, 0 changed, 0 destroyed`); `terraform state list | wc -l` returned 169 because the state also lists the data sources, which Terraform reads but does not create. In a plan, `+` means create, `~` means update in place, and `-/+` means destroy and re-create (replace), usually because an attribute that cannot be changed in place, such as the user data of an instance, has changed.

Changing one line of application code replaces the servers because the application is packaged by `archive_file`, uploaded as `app/<sha256>.zip`, and the SHA-256 is part of each server's user data (`app_sha` in `compute.tf`), while the module sets `user_data_replace_on_change = true`. I saw this when I fixed bug 9 in `app.py`: the plan was `5 to add, 0 to change, 5 to destroy`, replacing `aws_s3_object.app` and the web, onboarding, offboarding and dashboard instances, but not the NAT instance, whose user data does not include the application. This is the immutable-server model: servers are never patched by hand, every change produces new, known servers built from code, and drift inside a server cannot accumulate.

In G7 I changed the console rule by hand to `0.0.0.0/0`. Terraform found it because every `plan` refreshes the real state of each resource recorded in the state file and compares it with the configuration: it showed `~ aws_vpc_security_group_ingress_rule.web_console will be updated in-place` with `cidr_ipv4 = "0.0.0.0/0" -> "52.124.37.145/32"` (`1 to change`), and the apply restored the rule. CloudTrail recorded both `ModifySecurityGroupRules` calls (20:11:25 and 20:13:04 UTC), both under `lab-user`, because Terraform used the same credentials; only the user agent distinguishes them. A rule that someone *adds* by hand would not appear in this plan because it is a new rule resource with its own ID that is not in the state: Terraform only refreshes and compares the objects it manages, so it does not know the extra rule exists. Detecting that kind of change needs other controls, such as AWS Config rules, CloudTrail alerts on `AuthorizeSecurityGroupIngress`, or importing the resource.

## Q10 (explore). Prove it, then reflect

In H2 I opened a Session Manager shell on the web server and called the dashboard service (`https://10.20.11.11:5003/api/employees`). With no client certificate the result was `000`: the mutual TLS layer refused the handshake, so no HTTP response existed. With the certificate but no internal token the result was `401`, produced by the internal-token check (the dashboard logged `internal_auth_rejected` from `10.20.1.10`). With the certificate and the token but no administrator JWT the result was again `401`, produced by the JWT check. From the same server, `aws iam list-users` failed with `AccessDenied` because no identity-based policy of the `nimbus-web-svc` role allows `iam:ListUsers`; `aws s3 ls` failed with `AccessDenied` because "no VPC endpoint policy allows the s3:ListAllMyBuckets action", which shows that the S3 gateway endpoint policy is an extra layer in front of IAM; and an IMDSv1-style request for credentials (`/latest/meta-data/iam/security-credentials/` without a token) returned `401`.

IMDSv2 requires a session token obtained with an HTTP `PUT` and a special header before any metadata can be read. This protects against server-side request forgery (SSRF), where an attacker tricks the application into fetching a URL: most SSRF flaws can only send simple `GET` requests and cannot add the header, so they cannot steal the role's temporary credentials. A hop limit of 1 sets the IP time-to-live of the token response to one hop, so the token cannot travel beyond the instance itself, for example to a container, a proxy or a forwarded connection on the host; only processes running directly on the instance can use the metadata service.

Session Manager records what SSH does not: every session is started through an AWS API call authenticated by IAM, so CloudTrail logs `StartSession` with the IAM identity, time, source address and session ID (mine was `lab-user-s79x6zvnysio78tazr6476vooe`), and access is granted or revoked with IAM policies instead of shared key pairs. It can also stream the full session transcript (commands and output) to CloudWatch Logs or S3, and EventBridge can alert on sessions. With SSH, the server only knows a local Unix user and a key fingerprint in its own logs, which an attacker with root can erase; there is no central record of which person connected, and port 22 must be open (in this lab it is closed and there is no key pair at all).
